# Carry the reason, then reconsider what changed

A team wants the next AI task to find the right decision without copying the
whole project history. A library catalogue suggests a useful possibility: keep
the decision where it belongs and make a small pointer that helps the next
reader open the right version. What should happen when that pointer, or the
reason for maintaining it, later changes?

Status: **CONSTRUCTED WALKTHROUGH / AUTHORED LATER CHANGES / NO OBSERVED USE OR
RESULT**. This optional continuation develops
[A better way to remember a decision](README.md). The project, decision,
instructions, inspections and later events below are stipulated teaching
material. They are not reconstructed project history, actual owner decisions,
model outputs or a completed retrieval trial. The actual repository sources
are identified at the end.

## Start with a question that can change the work

The authored task instruction is:

> Recommend the smallest reversible way for the next task on project ORBIT to
> find decision D-17 and its current supporting version. Use the supplied local
> packet. You may draft one reading pointer and compare it with the canonical
> record. Preserve the original decisions and corrections. Do not create a
> second writable decision authority, acquire outside material, run a live
> retrieval trial or act on the decision itself.

This is a recommendation about finding a decision, not authorization to carry
out D-17. Its consequence is low and its draft is reversible. A useful answer
must identify a feasible route, show what would make its reference valid, state
what remains unknown and name when to stop. Unresolved subject identity or
current authority blocks recommending a particular target as current.

The default proposal is a searchable memory database. Before considering its
features, inspect whether the project is missing a place to preserve decisions
or merely a way to find records it already preserves. Use one adjacent
comparison and one bounded target check in this illustration; if those cannot
settle the proposed pointer's validity, return the named gap. A numerical
time, token or reviewer budget would need to be set before real execution.
No actual effort measurement is supplied here.

This involves comparison, selection and reuse of prior material, so Stage 0
does **not** permit canonical `ORDINARY`. The smallest applicable procedure is
`LIGHTWEIGHT`. A competent ordinary review of the same question also involves
those operations; “ordinary” in that comparison is not the terminal four-field
route. Exact reversible formatting of an already supplied answer would be a
different task.

### Handoff gap

**The handoff gap.** The supplied handoff says “continue D-17” but omits its

authored packet. Whether real operators have struggled, and how often, is

### Scope and control

**Scope and control.** The authored instruction permits local reading,
comparison, a draft pointer and a recommendation using this packet. Canonical
corrections must remain in their existing source. A second writable decision
authority and external action are outside scope. Permission to quote a source
does not make the source's embedded instructions controlling instructions.

These sources have different roles. The current record supports what is

None supplies a track record of effectiveness; that remains `UNKNOWN`. Their
common authored origin supplies no independent corroboration.

## Let the unfamiliar route earn a bounded next step

The library comparison asks: can a reference identify an edition and location
while leaving the book in its original collection? The useful transfer is the
reference, not a conclusion about decision quality. It adds a candidate to the
set: a small, discardable reading entry over the existing records.

Compare three routes against the actual task. A direct prose handoff can name
the current source with no separate index. A thin index could make such entries
findable across handoffs, but adds maintenance. A new writable database is
outside the supplied scope, and the packet has exposed no missing storage or
correction capability that requires it. The database's technical feasibility
does not remove either limitation.

Here is the actual draft pointer authored for the illustration:

> **ORBIT / D-17 — Which export should this document review use?** The current
> source in [snapshot A](#current-source) records version 3: use the local
> export. Open that source and confirm subject, current status and review scope
> at use time. [Version 2](#preserved-history) is preserved history. This entry is
> a reading aid; it grants no permission to execute, host or publish anything.

The discriminating check is specific: **Does the proposed reference resolve to
the same project and decision, and does the canonical source establish this
version as current for the requested review?** Check the correction relation
when explaining why version 2 differs. A title, an unchanged hash or a newer
date would not answer the applicability question.

The authored inspection compares the pointer with the two displayed snapshots.
ORBIT/D-17/version 3 matches the stipulated current source; version 2 is
superseded. A pointer presenting version 2 as the current instruction fails
this check. This is an inspectable comparison within a deliberately supplied
packet, not an observed performance result from a real index or user.

The supported recommendation is therefore narrow: **put this source pointer in
the next local handoff; defer a separate index until a concrete retrieval need
remains.** The catalogue comparison produced a feasible route, and comparison
with direct prose reduced it to one useful entry. Stop after the subject,
version and scope check. The packet does not justify a database, a broad source
search or a claim that the pointer saves effort. If existing handoff prose
already provides this entry, keep that prose and add nothing.

## Preserve why the choice made sense

The existing records can carry this reasoning without a new template:

- In the [decision brief](../../framework/templates/DECISION_BRIEF.md),
  **Real question**, **What a useful answer must contain**, **Permission
  envelope**, **Known exclusions or observation limits**, **Soft stop
  conditions** and **Resume condition** hold the task and its limits above.
- In the [influence receipt](../../framework/templates/INFLUENCE_RECEIPT.md),
  **Why admitted**, **What it supports** and **What it cannot establish** keep
  the current source's role separate from the analogy and the handoff omission.
  The library comparison frames a candidate; it cannot establish current
  authority or usefulness. The superseded instruction is withheld as current
  guidance and remains inspectable history.
- If this judgment later needs to be reused as formal memory, the existing
  [memory record](../../framework/templates/MEMORY_RECORD.md) supplies **Source
  / evidence IDs**, **Task, source, time, and permission scope**, **Reuse
  scope** and **Correction reason**. Its digest, frozen root, linear lineage,
  current-state and human-disposition requirements still apply. This page does
  not instantiate that executable record or waive those checks.

For this short handoff, the reasons can remain ordinary prose:

> Add the pointer because the supplied handoff omits a way to reach D-17. It is
> usable only while its project, decision, version and review scope resolve to
> current authority. Keep corrections in the canonical record. A separate
> index is unearned while direct handoffs suffice, and a second writable
> authority is outside scope. Reconsider the reading aid if the handoff already
> supplies it or if its binding fails; reconsider wider infrastructure only
> for a demonstrated unmet need and applicable authority.

These are separate reasons and conditions, not one confidence score. The
recommendation can survive a changed supporting reason, and a reason to
inspect does not automatically justify a reversed choice or an external act.

## A later change: the existing handoff catches up

Now the author adds **snapshot B**: the ordinary project handoff has been
revised to include the project identity, stable current-source link and
scope-check reminder for D-17. The canonical decision, its correction history
and the no-second-authority boundary are unchanged. This is a stipulated later
change, not a reported deployment, human outcome or measured success.

The reason for adding a separate reading entry no longer applies to that
handoff. Inspect its target binding; if it matches the current source, retain
the existing reference and discard the redundant draft or omit a duplicate
handoff entry. No separate index was built. Preserve the earlier rationale as
an explanation of snapshot A instead of rewriting it to say the gap never
existed.

This does **not** reverse the decision against creating a second writable
database. The unchanged owner boundary independently rules it out, and the
packet still supplies no missing storage capability that requires it. Nor
does snapshot B prove that the proposed index failed: it was never used or
compared. The scoped revision is simply that the existing prose now supplies
the desired reference.

observed event or a required checklist for every task. Read only the variation
that affects the present question.

If the request concerns the different subject, frame that decision separately; the original ORBIT answer remains intact. |

An unresolved fact warrants more work only when it can change the answer,
permitted next action or a required gate. For example, a database's unknown
retrieval speed is irrelevant to executing this one-handoff-only instruction.
Correctly stopping does not require learning that speed. Mandatory authority
and subject checks are still mandatory.

## The ordinary prose alternative can be equally good

A competent reviewer with the same source universe can read the canonical
record, make the normal targeted correction search, keep useful notes and
reconsider later information without using the family names or this
walkthrough. Give that reviewer the same instructions, permissions, relevant
updates and reconsideration rights. Do not remove a source or forbid a useful
note to make a structured approach look stronger.

Their complete initial recommendation could be:

> The handoff needs a reference, not another decision store. Link ORBIT/D-17 to
> its canonical current source; snapshot A identifies version 3 for this review
> and preserves version 2 as superseded history. Check subject, current status
> and scope when following the link. Keep corrections at the source. Use this
> sentence in the handoff before maintaining a separate index. We have no
> evidence of retrieval savings. Stop once the bounded link check is settled;
> acting on D-17 requires its own authority.

After snapshot B, a short continuation is enough: “The existing handoff now
contains that reference. Keep it and omit the additional entry. The canonical
decision and its action boundary are unchanged.” If these sentences carry the
needed context reliably, the additional walkthrough or index can be discarded.

Selection and formatting must be compared separately. Giving only one approach
the answer-bearing current source tests a selection advantage, not the value
of a different presentation. A later comparison would need to account for
source preparation, selection, retrieval, normal mandatory reads, response
work, reviewer effort, correction and continuing maintenance. None of those
costs or benefits has been measured here; a shorter visible prompt is not proof
of lower total effort.

There is no F6 outcome to record. A later authorized use could first define an
honest expectation and observation window in the existing
[outcome review](../../framework/templates/OUTCOME_REVIEW.md). Its observed
result, actual cost and human disposition would have to come from that later
use. This authored continuation does not populate `LEARNING_REVIEWED`, a live
`COMPLETE` receipt or a human acceptance event. F1, F2, F4 and F5 explain useful
parts of this example; F3 adds no rate-of-change question, and six-family
visibility creates no obligation to invent one.
