# Pattern Map v16 — opportunity expansion loops

Status: **AUTHORIZED LOCAL FEATURE-BRANCH WORK; NO MERGE, PUBLICATION, DEPLOYMENT, OR STUDY**

Baseline: `529852497109dc152928de642038d07b109a52e2`

## Purpose

The owner asked the primary orchestrator to execute a further improvement plan,
then run two additional opportunity loops with bounded subagents. This phase is
not v17 and does not reopen the locked thesis. Its purpose is to make the
existing v16 easier to understand, easier to share for review, and easier to
apply in a future project without turning the framework into mandatory
bureaucracy.

## Governing test

An addition is accepted only when it does at least one of the following without
creating a larger burden elsewhere:

1. shortens the path from first contact to the broad human idea;
2. makes a future mentor/public review more coherent without pretending it has
   occurred;
3. makes an agent or operator perform an observable action with less ambiguity;
4. makes transfer into a materially different project safer without claiming
   general validation; or
5. narrows a claim or research route using current primary evidence.

Detail, polish, novelty, or model enthusiasm alone are not acceptance reasons.
If existing artifacts already compose into the needed behavior, the correct
decision is to document that composition rather than add another artifact.

## Loop 0 — whole-project opportunity audit and bounded build

Three isolated lanes begin from the exact baseline and may edit only their
assigned paths:

| Lane | Question | Bounded output |
| --- | --- | --- |
| Public / mentor / visual | What is still missing between the local public candidate and a coherent private mentor or future X review package? | Unpublished publication-rehearsal assets, channel copy, decision checklist, and code-native visual candidates only where a written need exists |
| Agent / operator / transfer | Can a new project use v16 without reading the entire repository or manufacturing six-family ceremony? | The smallest composable adapter, worksheet, or executable contract that earns its existence; otherwise a documented no-build disposition |
| Research / claims | Does current primary work change the contribution ceiling, source route, or research opportunities? | A targeted, non-exhaustive verification report and bounded source/claim corrections; no study, provider, dataset, paper order, or result |

Every lane reads the locked contracts, works in an isolated Git worktree, runs
focused checks, and commits a coherent branch. Advisory interpretation remains
subject to the repository authority order.

## Loop 1 — cross-lane challenge and integration

After the first build, each lane challenges one other lane:

- the public lane asks whether agent-facing additions are understandable and
  proportionate for a thoughtful nontechnical reader;
- the agent lane asks whether publication assets actually help a project act or
  merely restate the essay; and
- the research lane asks whether either lane overstates novelty, effectiveness,
  generality, or readiness.

The primary orchestrator reproduces every material finding, records
`Accepted`, `Accepted with revision`, `Deferred`, or `Rejected`, and integrates
only reviewed commits. The locked owner-intent checksum must pass before and
after integration.

## Loop 2 — hostile removal, transfer, and public-surface red team

The integrated candidate receives a second independent loop:

1. **Removal test:** remove each new artifact conceptually. If the project is
   equally usable, the artifact is presumptively unnecessary.
2. **Cold-start transfer test:** a receiver gets only the intended entry point;
   missing authority, context, or stop conditions must fail closed.
3. **Public-surface test:** first contact remains the human problem and six
   families, not release machinery, a protocol, or agent notation.
4. **Claims test:** every new statement remains within the authored
   design/governance and testable-agenda ceiling.
5. **Proportionality test:** ordinary supplied-material work still exits before
   layered records; no new artifact becomes universally mandatory.

Accepted corrections receive focused regression tests. The complete owner
review runner and a clean-clone replay gate the final expansion checkpoint.

## Explicit boundaries

This phase may create local drafts, code-native candidate visuals, feature
branches, commits, pushes, and a draft pull request. It may browse public
primary sources for claim checking. It may not:

- edit `docs/OWNER_INTENT_V16.md` or its checksum;
- alter immutable archives;
- merge to `main`;
- deploy, publish, post to X, contact the mentor, or create a Release;
- set final byline, canonical URL, social handle, or public-release metadata on
  the owner's behalf;
- run an empirical, model-comparison, participant, or live-product study;
- select or call a research provider, acquire a corpus, spend money, or present
  fixtures and model reviews as results; or
- claim that transfer to Signal Foundry or any invented case validates v16.

## Stop condition

The expansion is terminal when:

- both post-build loops complete;
- every material finding is dispositioned;
- no reproduced P0/P1/P2 remains in the added surfaces;
- the complete existing acceptance runner still passes;
- the locked owner intent and permanent Echo separation are unchanged; and
- remaining work is limited to owner taste, physical/manual accessibility,
  publication-time identity/link decisions, downstream-repository authority,
  or separately authorized research.
